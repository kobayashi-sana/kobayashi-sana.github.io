x64 Windows ROP 初体验：没有 pop r9 gadget 时怎么办

本文是我的 Windows ROP 的入门笔记。本文主要讲解了如何在没有开启 GS 和 DYNAMICBASE 保护时如何对具有栈溢出漏洞的程序进行利用。利用使用了两条路径：直接 ROP 和 VirtualProtect 修改内存页为 RWX 执行 shellcode。

测试程序

编译命令：cl /Zi /W4 /GS- .\echo.c /link /DYNAMICBASE:NO

关于 VirtualProtect 那两行

这两行代码是为了在导入表中留下 VirtualProtect 函数，简化调用。

关于 0x8f0

在内核写入用户模式缓冲区时，内核会对缓冲区的权限进行校验，如果缓冲区所在的区域不可写，recv 函数会返回错误 WSAEFAULT（10014）。

0x8f0 是 recv 函数接收客户端消息的最大长度。这个值是通过调试得来的。我们先启动 echo.exe ，然后再使用 windbg 附加上去，主线程的栈的最高地址是 0x160000 。

服务端是单线程程序，阻塞在 accept 的线程就是主线程。在 WinDbg 的 Stack 窗口查看它的调用栈：

0x15f520 是 main 函数调用函数前的 rsp，而 main 函数的局部变量 buf 在 rsp+0x1f0 处。

我们使用 0x160000 减去 0x15f520 + 0x1f0（buf 的地址）就得到了 0x8f0。

这张调用栈截图还顺带回答了另一个问题：[0x5] 帧（main 的调用者）的 Child-SP 是 0x15ff20，即 main 的返回地址位于 0x15ff18，从它到栈上边界 0x160000 只剩 0xE8 字节。本文最终的 ROP 链共 29 个栈槽，总长恰好 0x8F0，链尾正好顶在栈上边界上——一个多余的 gadget 都放不下，后文链的紧凑设计全部是被这个约束逼出来的。

程序分析

这是一个 TCP 服务器，监听 9999 端口。客户端连接时，服务端发送 Echo Server 1.0\n 字符串到客户端，服务端接收客户端消息并写入栈缓冲区 buf 中，随后复制消息到全局缓冲区 echo 中，最后服务端回显客户端的消息。

如果接收到的消息长度 <= 0 则会停止接收消息，main 函数退出。

接收消息大小最多为 0x8F0 字节，栈缓冲区大小为 2048（0x800） 字节。如果客户端发送的消息大小超过 2048 字节，则会撑爆缓冲区，导致栈溢出。

栈帧与调用约定

我们先讲解一下 Windows 函数调用栈的结构。以main 函数调用 strcpy 函数为例，内存示意图如下：

Windows x64 ABI 使用寄存器传递函数调用的前四个参数，依次是 rcx、rdx、r8 和 r9 ，其余的使用栈传递。

相较于 Linux 的 System V AMD64 ABI，Windows 的 x64 ABI 要求调用者必须将栈指针（RSP）至少减少 0x20 字节，用于被调用者保存 rcx、rdx、r8 和 r9 四个易失寄存器。当然这部分空间也可以在 main 函数的序言中和局部变量统一分配。

如果我们仔细观察 IDA，就会发现 main 函数第一个局部变量位于 rsp+0x20 处，未使用的这部分空间就是 shadow space。

当然，Windows x64 ABI 也要求调用函数前 rsp 对齐 0x10 字节，也就是函数入口的 rsp 以 8 结尾。

利用

直接 ROP

我使用 ROP 的思路很简单：劫持 main 函数的返回地址为 win 函数的起始地址。

使用 IDA 查看栈变量，有注释 [rbp-808h]，这说明 buf 距离返回地址 0x808 字节。

char buf[2048]; // [rsp+1F0h] [rbp-808h] BYREF

buf 本身占 0x800 字节，与返回地址之间还有 8 字节的对齐 padding，因此 padding 长度取 0x808。

再双击 buf 变量，向下翻，发现没有保存的 rbp 寄存器，只有返回地址。

所以我们只需要 0x808 字节的 padding。

因为我们只调用 win 一个函数，不关心 shadow space，我们只关心栈对齐。

根据上面的示意图，如果直接调用 win，那么 win 的入口处 rsp 以 0 结尾，如果我们先垫一个 ret gadget，那么 win 入口的 rsp 以 8 结尾，栈就对齐了。

VirtualProtect

VirtualProtect 利用链的思路是先通过 strcpy 向 echo 写入无 \x00 的 shellcode，然后调用 VirtualProtect(echo, 0x1000, 0x40, 可写地址);，最后跳转到 echo 执行任意代码。

使用 ROPgadget 搜索整个 PE 文件，得到了 pop rcx ; cld ; ret 和 pop rdx ; ret 的 gadget。但是 VirtualProtect 有四个参数，r8 和 r9 的内容如何控制呢。

r8

关于 r8，我找到了一个 pop gadget：pop r8 ; mov ecx, dword ptr [rcx] ; add rsp, 0x20 ; pop rbp ; jmp 0x1400034b3。rcx 指向一个可读地址即可。但是最后有一个无条件跳转看起来有点棘手，跟踪一下。

这是一个 IAT 导入桩，调用了 LeaveCriticalSection 这个外部函数，前面的 mov ecx, dword ptr [rcx] 是在取 _Lock。

_acrt_lock_table 是一个 RTL_CRITICAL_SECTION 数组，长度为 15。查看 ReactOS 的源码发现_Lock 的值可以取 0 ~ 13，我这里用的 4。

如何让 _Lock 为 4 呢？因为这是一个 DWORD 值，直接从 PE 内存中搜索 04 00 00 00 这四个字节就可以了， windbg 搜索命令 s 0x140000000 L0xbb000 04 00 00 00。

控制了 r8，就可以尝试控制 r9 了。

r9

r9 没有 pop gadget，但是有一条 mov gadget：mov r9, rax ; jmp 0x14003b941，我们看一看 0x14003b941：

如果 dword [rcx+0x30] <= 0 && r10d == 0 则会跳出循环。但我们很难去控制 r10d，我们看看整个函数：

观察一下变量的注释，发现 r9 先后是 p_buffer 指针和循环变量 i。如果我们可以控制循环变量 i，就可以控制 r9（残留值）。

我们可以通过控制函数参数 number == 0 并且 dword [this+0x30] == 0 直接跳出循环。

我们分析 i 的值，首先它由 v7 初始化，来自于 &p_buffer->_member_buffer[2 * v6 - 2]，
v6 来自于上面的判断：如果 this->_buffer._dynamic_buffer._p != 0，v6 等于 this->_buffer._dynamic_buffer_size >> 2，否则等于 256。总之，i 是一个在 this 指针后面的指针。

因为 this 指向了初始化为 0 的 .data 节，因此 dword [this+0x30] 等于 0 成立。

因此，我们只需调用 type_case_integer_parse_into_buffer(&echo + len(shellcode), 0, 任意值) 即可在 r9 留下一个可写的指针。

在 VirtualProtect 入口处断下（bp 0x140008be0），寄存器的状态：

逐个核对四个参数：rcx = 0x1400ae220（echo）、rdx = 0x1000、r8 = 0x40（PAGE_EXECUTE_READWRITE）、r9 = 0x1400af270。注意 r9 恰好等于 echo + 0x1050，即 this + 0x50——与前面对 type_case_integer_parse_into_buffer 的分析所预测的残留值完全一致，理论与执行在这里闭环。另外 rdi = 0x2020202020202020，正是 ljust 填充的空格（0x20）残留在寄存器里的痕迹。

shellcode

使用 msfvenom 生成 shellcode，弹出计算器：

  • -p：指定 payload 类型
  • -b：排除坏字符 \x00

为什么要排除 \x00：strcpy 复制到第一个 \x00 就会停止，shellcode 中一旦出现 NUL 字节就会被截断，落进 echo 的就不再是完整的 shellcode。同理，exp 中 shellcode.ljust(0x808) 的默认填充字符是空格（0x20）而不是 \x00，保证截断点之前的内容完整到达 echo。而 ROP 链中的 gadget 地址带有 \x00（如 0x0000000140090f36 的高位字节），对 strcpy 来说恰好是天然的截断点，此时 shellcode 早已复制完毕，截断无害。
